## 1. Что это и зачем

Агенты меша заканчивают задачи, когда тебя нет у терминала. Результат оседает в заметке или в панели tmux, и его надо идти искать. Плагин разворачивает направление: **агент сам отчитывается тебе в Telegram** по завершении турна — коротко по умолчанию, с полным текстом файлом, когда он существенно длиннее сводки.

Паттерн скопирован с `~/dotfiles/claude/hooks/speak-summary.py` (Stop-хук читает транскрипт и озвучивает финал через TTS). Здесь то же самое, но доставка в Telegram и с сохранением полного ответа.

**Дыра, которую он закрывает.** В меше уже есть `page` — но это CRITICAL-тир с порогом-контрактом, рутина через него запрещена. Есть `log-bot-notify` — но это отчёт flow-keeper'а после батча. **Рутинного «агент закончил задачу» тира не было ни у кого.** Ради него всё и делалось.

## 2. Как работает

```
агент заканчивает турн
   └─ Stop-хук tg_summary.py
        ├─ читает transcript JSONL → последний текстовый блок ассистента
        ├─ сохраняет полный текст → <state>/answers/<id>.md
        ├─ строит сводку: текст после 📨, иначе первые 4 строки (потолок 600 симв.)
        └─ tg_deliver.deliver()
              ├─ есть log-bot-notify в PATH → шлёт через него   (хост меша)
              └─ нет → прямой Bot API тем же токеном           (чужой хост)
                 └─ файл прикладывается ТОЛЬКО выше порога
```

**Три слоя и кто чем владеет:**

| Слой | Файл | Чей |
|---|---|---|
| Producer — транскрипт → сводка + сохранённый ответ | `hooks/tg_summary.py` | этот плагин, бесспорно новая часть |
| Доставка — байты → Telegram | `scripts/tg_deliver.py` | **уже существовала** (SC1 / log-bot), плагин её только зовёт |
| Транспорт — Bot API | `scripts/tg_send.py` | фолбэк для хостов без рычага |

## 3. Главное архитектурное решение: своего транспорта нет

Изначально я построил собственный транспорт к Bot API. Разведка показала, что это ошибка:

- эпик **SC1 - Telegram Layer Convergence** держит ратифицированный инвариант «**ОДИН бот/токен, не строим параллельный транспорт**»;
- живой бот в системе один — `@finimch_bot`, токен в `.env` пакета `log-bot`;
- исходящий рычаг `log-bot-notify` уже есть и раскатан по всему флоту;
- `getUpdates`-слот занят демоном `com.mch.log-bot` под launchd, и он защищён flock'ом.

Поэтому внутри меша плагин **не разговаривает с Telegram напрямую** — зовёт рычаг. Свой Bot API остаётся только для хостов, где рычага нет (плагин ставится куда угодно, `log-bot` — специфичен для твоей системы).

**Решающий довод — не риск конфликта, а переживаемость флипа.** SC1 обязан однажды переключить backend на нативный `scion message --channel telegram`. Код, который зовёт Bot API напрямую из разных мест, этот флип не переживёт. Поэтому весь транспорт заперт в одной функции: когда флип случится, меняется одно место.

### Почему нет команды `/full <id>`

В исходной постановке было «полный ответ по запросу командой боту». **Построить нельзя**, и это не вопрос цены:

- команде нужен `getUpdates` — а слот занят демоном capture. Второй потребитель на том же токене **молча ворует апдейты**, и у Bot API нет истории, то есть сообщения теряются навсегда. Это уже происходило 02.07.
- второй бот ломает инвариант «один бот».
- плюс SC1 отдельно депрекнул corr-id и pending-table, а `/full <id>` — это ровно корреляция.

То есть команда потребовала бы отката двух ратифицированных решений. **Замена:** полный ответ пушится файлом рядом со сводкой. Исходящее, ничего не занимает.

Если pull-стиль всё же понадобится — правильный путь: flow-keeper отдаёт из стора по существующему capture-маршруту. Это запрос во `flow`, а не код здесь.

## 4. Что включено прямо сейчас

| Что | Состояние |
|---|---|
| Код плагина | влит в `main`, все фиксы внутри |
| **В публичный GitHub не ушло** | push ждёт твоего решения |
| Пилотный хук | включён в настройках агента `epic-tg-bot` — сделал `orchestrator`, это его lane |
| Путь хука | замороженный worktree `m-claude__pilot-tg-report`, пришпилен к коммиту с фиксами |
| Активация | хуки читаются при старте сессии — работает со следующей сессии агента |

Точные хэши, расхождение с `origin/main` и протокол приёмки мёрджа — в
[`docs/handover-tg-report-ru.md`](../../docs/handover-tg-report-ru.md) (документ `epic-mclaude`,
владельца репозитория). Здесь я их не дублирую: они устаревают на каждом коммите.

**Почему отдельный worktree.** Сначала хук указывал на основное рабочее дерево. Это ломалось: плагин существовал только на ветке, и любое переключение репо на `main` убивало хук на каждом турне. `orchestrator` перевёл пилот на замороженную копию.

**Побочный эффект, который надо помнить:** пилот пришпилен к конкретному коммиту, свежие правки в него **не едут сами**. Один раз это уже стреляло — фиксы дефектов лежали в ветке, а пилот крутил старый код, пока снапшот не обновили вручную.

## 5. Настройки

На хосте меша не нужно ничего — рычаг уже знает бота.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `TG_REPORT_TRIGGER` | `📨` | текст после этого эмодзи становится сводкой |
| `TG_REPORT_SUMMARY_LINES` | `4` | сколько строк брать, если эмодзи нет |
| `TG_REPORT_SUMMARY_CHARS` | `600` | жёсткий потолок сводки |
| `TG_REPORT_ATTACH_THRESHOLD` | `1500` | приложить файл, если ответ длиннее; `0` — никогда |
| `TG_REPORT_RETENTION_DAYS` | `14` | сколько хранить сохранённые ответы |
| `TG_REPORT_STATE_DIR` | `$XDG_STATE_HOME/tg-report` | где лежит стор ответов |
| `TG_REPORT_FORCE_DIRECT` | не задано | `1` — обойти рычаг, только для отладки |

Креды фолбэка (нужны, **только** если рычага нет): `TG_REPORT_BOT_TOKEN` / `TG_REPORT_CHAT_ID`, либо `LOG_BOT_TOKEN` / `TELEGRAM_USER_ID`, либо файл `~/.config/tg-report/config.json` вида `{"bot_token": "...", "chat_id": "..."}` с правами `0600`.

**Секретов в репозитории нет и быть не может** — ни один путь в коде не пишет их сюда.

### Порог вложения — почему именно такой

Файл прикладывается, когда выполнены **оба** условия: ответ не короче 1500 символов **и** длиннее удвоенной сводки. Первое отсекает шум, второе — файл, который просто дублирует уже отправленное сообщение.

Отправлять файл на каждое завершение было запрещено на ревью, и довод верный: канал, который сыплет файлами, ты выключишь целиком, и фича умрёт от собственного успеха.

## 6. Гарантии безопасности (и почему они здесь)

Три свойства держатся **тестами, а не обещаниями**. Каждое появилось после конкретного дефекта.

### 6.1. Только исходящий, навсегда

В плагине нет ни строки `getUpdates` и никакого webhook. Проверяет `tests/test_no_inbound.py`: разбирает исходники через `ast`, снимает докстринги (чтобы можно было писать *о* запрете) и падает, если запрещённое имя появится в исполняемом коде. Отдельный тест доказывает, что проверка поймала бы подсаженное нарушение — проверка, которая не может провалиться, ничего не проверяет.

Зачем так строго: второй потребитель входящих на общем боте необратимо крадёт твои сообщения.

### 6.2. Стор не удаляет чужие файлы

`TG_REPORT_STATE_DIR` — ввод оператора. Раньше prune сносил **любой** `*.md` старше 14 дней под этой директорией: один неверный экспорт на папку заметок — и тихая потеря данных.

Теперь для удаления нужны **два независимых условия сразу**: имя файла должно совпадать с шаблоном сохранённого ответа (`<6 hex>.md`) **и** в директории должен лежать маркер `.tg-report-store`, который плагин пишет сам. Директорию, которую плагин не создавал, он не трогает вообще.

Тесты написаны со стороны атаки: кладу `important-note.md` возрастом 400 дней в «папку заметок» и проверяю, что он выжил.

Ответы пишутся `0600` в директории `0700` — сохранённый ответ это дословный транскрипт того, чем агент занимался.

### 6.3. Доставка не может пережить хук

Stop-хук выполняется **внутри твоего турна** — каждая секунда здесь это секунда зависшей сессии. Раньше хуку давалось 30 секунд, а доставка могла занять до 80. Симптом был бы не падением, а зависанием на каждом турне с убийством хука посреди отправки.

Теперь бюджет объявлен один раз (`TEXT_TIMEOUT + DOCUMENT_TIMEOUT` = 23 секунды) и **сравнивается тестом** со значением `timeout` прямо из `hooks.json`, с запасом на старт интерпретатора.

### 6.4. Токен не течёт в логи

Токен сидит в URL запроса, а некоторые ошибки `urllib` цитируют этот URL целиком в тексте исключения. Раньше такое исключение проходило мимо обработчика и печаталось в stderr. Теперь ловится, и **все** строки ошибок чистятся от токена.

### 6.5. Хук не может сломать работу

Любое исключение внутри → `exit 0`. Канал отчётности не имеет права ломать работу, о которой отчитывается. Если плагин не настроен — молча ничего не делает.

## 7. Интерим-долг: путь вложений

**Это временный долг, а не архитектура.**

Рычаг `log-bot-notify` умеет **только текст** — сигнатура `send(text: str)`, эндпоинт зашит на `sendMessage`. Поэтому вложения ходят в Bot API напрямую даже на хосте меша.

Долг ратифицирован с условиями: путь заперт в одной функции `_deliver_document()`, тем же токеном, по-прежнему исходящий, и удерживается там тестом. Уходит вместе с флипом SC1.

### ⚠️ Ловушка для того, кто будет делать флип

Целевой backend умеет вложения — у `scion message` есть флаг `--attach`. Но по его же справке он берёт пути **только под `/workspace` или `/scion-volumes`**, а *«абсолютные пути вне этих корней молча дропаются при доставке»*.

Стор ответов лежит вне обоих корней. **Наивный флип даст «отправлено успешно, файла нет»** — тихая потеря, худший класс дефекта. При флипе нужно либо перенести стор под принятый корень, либо класть туда копию перед отправкой.

## 8. Что НЕ входит в этот плагин

Границы зафиксированы решением Area, нарушать их не следует:

- **Кто репортит, как часто, тихие часы** — это тиринг, движок `flow`. SC1 явно вынес порог и анти-инфляцию туда.
- **Раскатка по флоту** — `orchestrator` / harness-config.
- **Сам телеграм-слой** — `area-scion` / SC1.

**Практический вывод: не включать больше одного агента, пока у `flow` нет движка тиринга.** 20+ агентов × каждый турн = поток, который убьёт канал раньше, чем принесёт пользу.

## 11. Известные ограничения

- **Ловит только завершение турна.** Агент, умерший без финального ответа, не отчитается. Расширение — подписка на события хаба, не сделано.
- **Сводка тупая по устройству.** Либо текст после `📨`, либо первые строки. Никакой суммаризации моделью — это дало бы задержку и стоимость внутри твоего турна.
- **Пилот пришпилен к коммиту** — правки не доезжают, пока снапшот не обновят.
- **На хосте без `log-bot-notify`** нужен токен в окружении или конфиге, иначе плагин молча промолчит (это осознанное поведение, а не сбой).

## 12. Честно о процессе

Две вещи, которые стоит знать при чтении этого кода:

**Транспорт был написан зря.** В постановке стояло «изучи существующий канал, прежде чем писать своё». Я запустил разведку и **параллельно** написал транспорт целиком с тестами. Разведка вернулась и сообщила, что такой транспорт уже есть и защищён ратифицированным решением. Код не выброшен — стал portable-фолбэком, — но делать его не следовало.

**Настройки агента лежат не там, где кажется.** У агента песочный `$HOME`
(`/Volumes/mch/.scion/agents/<slug>/home`), поэтому `~/.claude/settings.json` внутри его сессии
и твой `~/.claude/settings.json` — **разные файлы**. Я на этом попался: прочитал твой, увидел
отсутствие записи и почти поднял ложную тревогу, что хук исчез. Команда в пункте 9.4 указывает
на правильный файл.

**Первые 59 тестов пропустили три реальных дефекта** (пункты 6.2–6.4). Все три нашёл `epic-mclaude` на ревью — **чтением кода, а не по именам тестов**. Общая причина: тесты проверяли *объявленное* (таймаут передан, функция вызвана), а не *сходящееся* (бюджет доставки против бюджета хука). Новые проверки сравнивают конфиг с кодом и имеют негативный контроль.
